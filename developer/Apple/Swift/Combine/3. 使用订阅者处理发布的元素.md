# 使用订阅者处理发布的元素

施加背压以精确控制发布者生成元素的时机。

## 概述

在 Combine 中，发布者生成元素，订阅者对接收到的元素进行操作。然而，发布者必须在订阅者附加并请求元素后才能发送元素。订阅者还通过使用 Subscribers.Demand 类型来控制发布者交付元素的速度，以此表明其可接收的元素数量。订阅者可通过以下两种方式之一表示需求：

* 通过在订阅者首次订阅时由发布者提供的订阅实例上调用`request(_:)`方法。
* 当发布者调用订阅者的`receive(_:)`方法传递元素时，返回新的需求。

需求具有累加性：若订阅者已请求两个元素的需求，随后又请求`Subscribers.Demand(.max(3))`，则发布者的未满足需求将增至五个元素。若发布者此时发送一个元素，未满足需求将减少至四个。发布元素是减少未满足需求的唯一途径；订阅者无法请求负需求。

许多应用仅通过操作符`sink(receiveValue:)`和`assign(to:on:)`分别创建便捷订阅类型`Subscribers.Sink`与`Subscribers.Assign`。这两类订阅者初次连接发布者时即发出无限需求。一旦发布者存在无限需求，订阅者与发布者之间便不再进行需求协商。

## 随着发布者生成元素时消费它们

当发布者需求量高或无限时，其发送元素的速度可能超过订阅者处理能力。这种情况可能导致元素丢失，或因元素在等待处理时填满缓冲区而造成内存压力急剧上升。

若使用便捷订阅器，此情况可能发生，因其要求接收无限数量元素。请确保提供给`sink(receiveValue:)`的闭包及`assign(to:on:)`的副作用符合以下特性：

* 不要阻塞发布者。
* 不要通过缓冲元素消耗过多内存。
* 不要因不堪重负而无法处理元素。

幸运的是，许多常用发布器（如与用户界面元素关联的发布器）以可控的速率进行发布。其他常见发布者仅生成单一元素，例如 URL 加载系统的`URLSession.DataTaskPublisher`。使用这些发布器时，完全可以安全地使用 sink 和 assign 订阅者。

## 使用自定义订阅者施加背压

要控制发布者向订阅者发送元素的速度，请创建`Subscriber`协议的自定义实现。通过该实现指定订阅者可满足的需求量。订阅者接收元素时，可通过向`receive(_:)`返回新需求值，或调用订阅对象的`request(_:)`方法请求更多元素。两种方式均可让订阅者实时微调发布者在任意时刻可发送的元素数量。

这种通过向订阅者发出接收就绪信号来控制数据流的概念称为反压机制(back pressure)。

每个发布者都会追踪当前未满足的需求量，即订阅者请求的剩余元素数量。即使是 Foundation 的`Timer.TimerPublisher`这样的自动化源，也仅在存在待处理需求时才会生成元素。以下示例代码演示了该行为：

```swift
// Publisher: Uses a timer to emit the date once per second.
let timerPub = Timer.publish(every: 1, on: .main, in: .default)
    .autoconnect()

// Subscriber: Waits 5 seconds after subscription, then requests a
// maximum of 3 values.
class MySubscriber: Subscriber {
    typealias Input = Date
    typealias Failure = Never
    var subscription: Subscription?
    
    func receive(subscription: Subscription) {
        print("published                             received")
        self.subscription = subscription
        DispatchQueue.main.asyncAfter(deadline: .now() + 5) {
            subscription.request(.max(3))
        }
    }
    
    func receive(_ input: Date) -> Subscribers.Demand {
        print("\(input)             \(Date())")
        return Subscribers.Demand.none
    }
    
    func receive(completion: Subscribers.Completion<Never>) {
        print ("--done--")
    }
}

// Subscribe to timerPub.
let mySub = MySubscriber()
print ("Subscribing at \(Date())")
timerPub.subscribe(mySub)
```

订阅者的`receive(subscription:)`实现会在向发布者请求任何元素前延迟了五秒。在此期间，发布者存在且拥有有效的订阅者，但需求为零，因此不会发布元素。只有当延迟结束且订阅者发出非零需求时，它才会开始发布元素，如下输出所示：

```
Subscribing at 2019-12-09 18:57:06 +0000
published                             received
2019-12-09 18:57:11 +0000             2019-12-09 18:57:11 +0000
2019-12-09 18:57:12 +0000             2019-12-09 18:57:12 +0000
2019-12-09 18:57:13 +0000             2019-12-09 18:57:13 +0000
```

此示例仅请求三个元素，并在五秒延迟到期后发出请求。因此发布者在发送第三个元素后不再发送更多元素，但也不会通过发送`Subscribers.Completion.finished`值来完成发布，因为发布者仍在等待更多请求。订阅者若要持续接收元素，可存储订阅并定期请求更多元素，也可通过其`receive(_:)`实现的返回值来表示新需求。

## 使用背压操作符管理无限需求

即使不编写自定义订阅器，您仍可通过使用 Combine 的缓冲或计时运算符来施加反压：

* `buffer(size:prefetch:whenFull:)`从上游发布者处保留固定数量的项目。当缓冲区已满时，它会丢弃元素或抛出错误。
* `debounce(for:scheduler:options:)`仅在上游发布者停止发布指定时间间隔后才进行发布。
* `throttle(for:scheduler:latest:)`以指定最大速率生成元素。若在某个时间间隔内收到多个元素，则仅发送最新或最旧的元素。
* `collect(_:)`和`collect(_:options:)`会将元素打包，直到它们超过指定数量或时间间隔，然后向您发送一个元素数组。如果您的订阅者能够同时处理多个元素，此选项非常适合。

由于这些操作符控制着订阅者接收的元素数量，因此您可以附加一个请求无限元素的订阅者，例如 `sink(receiveValue:)`和`assign(to:on:)`操作符。
