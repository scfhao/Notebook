# 如何高效评审代码：一位 GitHub 高级工程师的理念

GitHub 高级工程师萨拉·韦尔斯（Sarah Vessels）探讨了她的代码评审理念、优质代码评审与劣质代码评审的区别、她查找和评审代码的策略，以及如何从他人对自己代码的评审中收获最大价值。

我将代码审查视为工作中最重要的环节之一。事实上，每当看到同事有拉取请求等待代码审查时，我更愿意放下手头正在处理的分支，去审核他们提出的变更。毕竟，他们的拉取请求已经通过了持续集成（CI）的层层考验，也达到了他们自己认定的“完成”标准，所以它可能比我正在进行的工作更接近可交付状态。我更愿意帮他们的代码顺利完成，而不是再花费未知的时间去完善自己的代码。

## 什么是代码审查？

严格来说，代码审查——通过 GitHub 上的拉取请求审查进行——允许协作者对拉取请求中提出的变更发表评论、表示对这些变更的认可，或在拉取请求合并前要求进一步修改。

## 是什么让一次代码评审变得好或坏？

作为评审人员，沟通清晰是关键。你需要明确区分哪些意见是个人偏好，哪些是阻碍代码通过审批的关键问题。举例说明你建议的处理方法，能让你的代码评审更有水平，也能让你的意图更加明确。如果能从该拉取请求所在的代码仓库中举例说明，效果会更好——这能推动实现方式的一致性，进一步支撑你的建议。

相比之下，糟糕的代码评审缺乏清晰度。例如，直接批准或拒绝而不附带任何评论，可能会让拉取请求的提交者怀疑评审是否全面。即便只是在批准时重申你对提交者意图的理解，也能明确你和提交者是否达成了一致的认知。

如果代码评审中没有明确说明建议的实施时机，对提交者来说也可能是一次糟糕的体验。可以指出现有未修改的代码需要重构，或者需要处理额外的用例，但关键是要明确说明这些建议是否是审批的前提条件。如果拉取请求在没有你的建议的情况下也可以合并，请务必说明这一点。保持较小的代码差异并将这些更改单独提交，作为独立的拉取请求，可能会更稳妥。

示例：“我注意到你的新方法与该文件中现有的风格保持一致，接收了[X]个参数。参数过多会影响可读性，也意味着该函数承担了过多的职责。你觉得是否可以在后续的拉取请求中重构这个方法以及现有的方法，减少它们的参数数量？”

## 如何做好代码评审

### 提问

作为拉取请求的作者，我很乐意收到问题。当有人提出问题时，这为我提供了空间来解释为何对自己的修改充满信心，必要时还会引用相关问题、查询或图表。这也让我能与他人分享我的知识和经验。不仅作者能看到我的回复，其他审核者以及日后想要追溯过往决策背景的读者也能看到。

## 提供肯定语

除了提出问题之外，对拉取请求中你认可的部分发表评论也是一种良好做法。这些评论可以表明你已阅读并理解了所做的更改，或者你验证了代码中的某些假设。以下是几个示例：

* “看起来这与该模块中其他类所使用的模式相符。”
* “谢谢你为此添加了一个测试！”
* “这比以前可读性强多了。”

## 注意偏见与假设

我也非常支持初级开发人员在代码审查时向高级开发人员提问，即便他们觉得自己的问题很愚蠢或者答案显而易见。如果你觉得某个问题不明白，这完全合理。别人也可能对此感到困惑！尽管提出问题，给作者留出写下答案的空间，同时也为后来的人留存下这份知识。
