How we vibe code at a FAANG.
Hey folks. I wanted to post this here because I've seen a lot of flak coming from folks who don't believe Al assisted coding can be used for production code. This is simply not true.
For some context, I'm an Al SWE with a bit over a decade of experience, half of which has been at FAANG. The first half of my career was as a Systems Engineer, not a dev, although I've been programming for around 15 years now.
Anyhow, here's how we're starting to use Al for prod code.
1. You still always start with a technical design document. This is where a bulk of the work happens. The design doc starts off as a proposal doc. If you can get enough stakeholders to agree that your proposal has merit, you move on to developing out the system design itself. This includes the full architecture, integrations with other teams, etc.
2. Design review before launching into the development effort. This is where you have your teams design doc absolutely shredded by Senior Engineers. This is good. I think of it as front loading the pain.
3. If you pass review, you can now launch into the development effort. The first few weeks are spent doing more documentation on each subsystem that will be built by the individual dev teams.
4. Backlog development and sprint planning. This is where the devs work with the PMs and TPMs to hammer out discrete tasks that individual devs will work on and the order.
5. Software development. Finally, we can now get hands on keyboard and start crushing task tickets. This is where Al has been a force multiplier. We use Test Driven Development, so I have the Al coding agent write the tests first for the feature I'm going to build. Only then do I start using the agent to build out the feature.
6. Code submission review. We have a two dev approval process before code can get merged into man. Al is also showing great promise in assisting with the review.
7. Test in staging. If staging is good to go, we push to prod.
Overall, we're seeing a ~30% increase in speed from the feature proposal to when it hits prod. This is huge for us.
TL;DR: Always start with a solid design doc and architecture. Build from there in chunks. Always write tests first.

我们在FAANG是如何进行Vibe Code的。
大家好。我想在这里发布这个内容，因为我看到很多人批评说AI辅助编码不能用于生产代码。这完全不是真的。
给大家一些背景信息，我是一名AI软件工程师，有十多年的经验，其中一半时间在FAANG工作。我职业生涯的前半段是作为系统工程师，而不是开发人员，尽管我已经编程大约15年了。
无论如何，以下是我们开始在生产代码中使用AI的方式。
1. 你仍然总是从技术设计文档开始。这是大部分工作发生的地方。设计文档最初是一个提案文档。如果你能获得足够多的利益相关者同意你的提案有价值，你就继续开发系统设计本身。这包括完整的架构、与其他团队的集成等。
2. 在开始开发工作之前进行设计审查。在这里，你的团队设计文档会被高级工程师彻底审查。这很好。我认为这是把痛苦提前了。
3. 如果你通过了审查，你现在就可以开始开发工作了。前几周花在为将由各个开发团队构建的每个子系统做更多的文档工作上。
4. 待办事项开发和冲刺规划。在这里，开发人员与PM（产品经理）和TPM（技术项目经理）一起制定各个开发人员将工作的离散任务和顺序。
5. 软件开发。终于，我们现在可以动手敲键盘，开始完成任务工单了。在这里，AI已经成为一个力量倍增器。我们使用测试驱动开发，所以我让AI编码代理先为我将要构建的功能编写测试。只有在那之后，我才开始使用代理来构建功能。
6. 代码提交审查。在代码可以合并到主分支之前，我们有一个双人审批流程。AI在协助审查方面也显示出巨大的潜力。
7. 在预发布环境中测试。如果预发布环境一切正常，我们就推送到生产环境。
总的来说，我们看到从功能提案到上线生产环境的速度提高了约30%。这对我们来说是巨大的。
总结：始终从扎实的设计文档和架构开始。在此基础上分块构建。始终先编写测试。
