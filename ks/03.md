查詢執行計畫分析與查詢改寫技巧（10 項評分）
題目背景

你是 PostgreSQL 資料庫管理員。資料表結構與資料量如下：
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(100) UNIQUE,
    status VARCHAR(20)      -- 'active', 'inactive'
);  -- 約 200 萬筆

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id),
    amount DECIMAL(10,2),
    status VARCHAR(20),     -- 'pending', 'completed', 'cancelled'
    created_at TIMESTAMP
);  -- 約 8000 萬筆
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_orders_status_amount ON orders(status, amount);


一個報表查詢執行極慢，原始 SQL 如下：
SELECT * 
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed' OR o.status = 'pending' OR o.amount > 1000;

另外還有兩個慢查詢需要優化：

查詢 A（尋找從未下單的活躍使用者）：

SELECT id, name, email FROM users
WHERE status = 'active' AND id NOT IN (SELECT user_id FROM orders);

查詢 B（尋找金額為 100, 200, 300 的訂單）：
SELECT * FROM orders WHERE amount = 100 OR amount = 200 OR amount = 300;

10. 改寫多個 OR（程式碼填空）
將查詢 B 改寫為使用 = ANY 陣列運算子的版本：
SELECT * FROM orders
WHERE amount = ANY(_______);

---

第 1 題
Seq Scan、Seq Scan
說明：兩個表都使用了順序掃描，無索引掃描。
第 2 題
125000.00（或 125000）
說明：Hash Join 節點的第二個成本值為 125000。
第 3 題
79920000、低
說明：過濾掉 7992 萬筆，僅保留 8 萬筆，選擇性極低。
第 4 題
複合索引 (status, amount) 對於 status IN ('completed','pending') 可能仍有效，但第三個條件 amount > 1000 與 status 是 OR 關係，最佳化器無法合併索引掃描，評估全表掃描成本更低（因需要掃描大量資料）。
說明：OR 條件連接不同欄位時，索引通常無法同時使用。
第 5 題
將查詢拆成兩部分：
條件1：status IN ('completed','pending') → 可使用 (status, amount) 索引
條件2：amount > 1000 → 可使用 (amount) 索引（或強制索引）
然後用 UNION ALL 合併結果。
說明：分而治之，讓每個子查詢都能走索引。
第 6 題
o.id AS order_id, o.amount, o.status
說明：明確列出 orders 表的必要欄位，減少網路傳輸量。
第 7 題
UNION ALL
說明：UNION 會執行排序去重，UNION ALL 直接合併，更快。
第 8 題
o.user_id = u.id
說明：NOT EXISTS 子查詢必須關聯外表。
第 9 題
NOT IN 子查詢若回傳 NULL，整個條件會變成 UNKNOWN，導致查詢結果為空，遺漏應有的資料。
說明：三值邏輯下，x NOT IN (1, NULL) 等價於 x != 1 AND x != NULL，結果為 UNKNOWN。
第 10 題
ARRAY[100, 200, 300]
說明：= ANY(array) 等效於多個 OR 條件。
